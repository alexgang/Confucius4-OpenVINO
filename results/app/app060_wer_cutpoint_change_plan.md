## 1. 现状：App 的切点是怎么定的（代码事实）

`live_caption/live_caption_app.py::Segmenter.due()`（L914-987）三条出口：

| 规则 | 条件 | 常量 | 可调？ |
|---|---|---|---|
| 规则 0（硬切） | `dur >= MAX_SEG_SEC` | **20.0 s** | 写死 |
| 规则 2（静音超时，**优先**） | 段尾连续静音 ≥ `SILENCE_CUT_SEC` **且** 语音覆盖率达标 | **0.8 s** | 环境变量 `LIVECAP_SILENCE_CUT_SEC` |
| 规则 1（常规） | `dur >= MIN_SEG_SEC` **且** 最近 `SIL_LOOKBACK_SEC` 内有 ≥300 ms 静音 | **6.0 s** / **3.0 s** | `LIVECAP_MIN_SEG_SEC` |

切点**落点**（`live_caption/seg_stream.py`）：
- 规则 1 ⇒ `find_silence_in_range()` 取**最长静音段的中点**（`best_start + best_len//2`）；
- 规则 2 ⇒ `find_trailing_silence()` 取**紧贴末尾那段连续静音的起点**。

🔴 **可疑点 A：规则 1 的切点取「静音段中点」**
⇒ 静音段里**中点**可能仍落在词中间（例如 300 ms 静音里，前 100 ms 是词尾的
释放段、后 200 ms 是真正静音 ⇒ 中点落在词尾 ⇒ **段尾把词切一半**）。
🔴 **可疑点 B：规则 2 的切点取「静音起点」**
⇒ 静音起点**之前**那个音素的能量尾巴会被划给上一段的**尾部** ⇒ 同样切词。
🔴 **可疑点 C：静音判据是「帧能量 < 相对门限」**
⇒ 能量下降的**过渡区**（音节尾部的低能量部分）算静音 ⇒ 切点天然偏早
   ⇒ 切点**总是落在词的衰减侧** ⇒ 段尾丢半词、段首重复半词（ASR 侧观察到的现象）。

## 2. 候选改法（**都不动手**，等裁定）

> 每个方案都给出：**改什么 / 预期影响 / 代价 / 验证方式 / 风险**。

### 方案 ①「切点对齐到词边界」——**优先推荐**

- **改什么**：切点不再取「静音段中点」/「静音起点」，而是取**静音段内能量回升前的
  最后一次「过零」/低能量帧的起点**（即让切点落在**词与词之间**），
  或在解码侧做「切点回退到最近词边界」的**后处理**。
- **预期影响**：直接针对「边界/词 1.611×」⇒ 若边界错误率回到 BASE 的 9.93%，
  按 §45.2 的分解口径，WER 缺口可**大部分**收敛。
- **代价**：需要 ASR 侧给出「词边界」信息（或解码后做一次边界对齐）⇒ **跨模块依赖**。
- **验证方式**：**必须重跑推理**（🔴 铁律：「重聚合/重新切分类反事实若不重新解码 ⇒
  token 序列不变 ⇒ Δ=0.0 是数学必然」⇒ 只重切不重跑**测不出任何东西**）。
- **风险**：🔴 若 ASR 的 Opus 复核结论是「切点根本不是词边界问题」，本方案**白做**。

### 方案 ②「放宽静音判据 + 延长切点回退」

- **改什么**：`SILENCE_CUT_SEC` 0.8 → **1.2~1.5 s**（或 `MIN_SILENCE_MS` 300 → **500**），
  并把规则 1 的切点从「中点」改成「**静音段起点**」（更保守 ⇒ 切点更晚 ⇒ 更不容易切词）。
- **预期影响**：段数**下降**（538 → 接近 226）⇒ 边界总个数减少 ⇒ 缺口收敛。
  ⚠️ 但段变长 ⇒ **字幕延迟上升**（白字变慢）⇒ 需与「实时性」指标一起看。
- **代价**：🔴 **产品体感代价明确**（字幕变慢）；`SILENCE_CUT_SEC` 已是环境变量 ⇒ 改默认值即可，不需改结构。
- **验证方式**：同上，**必须重跑推理**；且要同时量「白字延迟」与「段数」。
- **风险**：段变长 ⇒ 译文首字更晚 ⇒ 与 TTS 首包叠加 ⇒ **可能恶化 §48 修的首包**。

### 方案 ③「段端点做去重」（缝合，不改切点）

- **改什么**：段首若与上一段尾有**前缀/后缀重叠**（ASR 侧观察到的「段首段尾重复」），
  在**拼接层**去掉重复部分（保留更长的那个）。
- **预期影响**：直接压掉**重复类**错误（§45.2 的 `rep` 列：APP_A 676 vs BASE 451）。
- **代价**：🔴 属于「显示层去重」⇒ 与 MT 侧的「翻译去重 ≠ 显示去重」铁律**同一类坑**
  （ASR 复读是真实的 ⇒ 全局去重会**丢真实内容**）⇒ 只能做**相邻段**的局部去重。
- **验证方式**：**纯后处理，不需重跑推理** ⇒ 🔴 但按铁律，「不重新解码的重聚合对照」是恒等式
  ⇒ 这里改的是**拼接结果**（不是聚合同一批 token）⇒ **不是恒等式**，可直接量 WER 变化。
- **风险**：🔴 可能吃掉**真实的重复**（演讲里确实重复的话）⇒ 需人工抽看。

### 方案 ④「换回 fp16 encoder」（§45.6⑤ 的直接对应）

- **改什么**：App 默认 ASR 引擎的 encoder 从 `int8asym` 换回 `fp16`。
- **预期影响**：§45.3 给的**上界只有 +0.113 pp**（fp16→int4 端到端）⇒ **量级不够**。
- **代价**：IR 体积 303.8 → **605.6 MiB**（+302 MiB）。
- **结论**：❌ **不推荐**（与 §45.3 的量化结论冲突：不是主因）。

### 方案 ⑤「改生成预算」

- **改什么**：`adaptive_budget` / finish max64。
- **预期影响**：§45.3 **已排除**（`c048 baseline` WER 17.723% 比 BASE 高 9.966 pp，
  远大于 App 整个缺口；App 与 BASE adaptive 同口径）。
- **结论**：❌ **不推荐**（已排除）。

## 4. 若 reviewer 裁定「做」，App 侧的落地顺序（**现在不执行**）

1. 先做**方案 ③**（纯后处理、可立刻量、不需重跑推理）⇒ 拿到「去重能收回多少 pp」，
