Confucius4-R2T2 流式推理：OpenVINO vs CUDA 对比报告

测量时间 2026-10-15 22:49 ｜ 同一台机器、同一段音频 test.wav（6.74 s / 16 kHz / mono / PCM16）｜ OV 2026.4.1（segment-encoder FP16 + INT8-past stateful） vs CUDA 13.3 / audio.cpp v0.9.1（GGUF Q8_0）

一句话结论

精度追平61-min 英文会议集上，OV 流式 WER 7.88% vs CUDA 官方流式 7.69%，差 +0.19 pp。修复自适应生成预算（C-047）之前的 17.87% 是 OV 端口自身的 bug，不是精度差距。
OV 以交付配置（640 ms 块）即可流式 同机同音频下 OV iGPU RTF 0.642（< 1，实时可跑），CUDA RTF 0.544。 稳态吞吐 OV 1.82× 实时 vs CUDA 5.78× 实时，差 3.18×。
代价是块长差一倍OV 用 640 ms 块才换来 RTF < 1；CUDA 在 320 ms 块就有大量余量。 若强行把 OV 也降到 320 ms 块，RTF 会涨到 1.101，失去实时性 —— 这正是本报告把 640 ms 作为主轴的原因。
已被端到端验证交付的 `mic_asr_app.py` 走的就是 640 ms 这套：麦克风 16 kHz → 在线 VAD（12–20 s 切段）→ 增量解码 → GUI 上屏。60 s 连续实测 RTF 0.650、5 段定稿、文本连贯无跨段重复。

⚠️ 先回答一个问题：为什么本报告主轴是 640 ms，而不是和 CUDA 一样的 320 ms？
因为 640 ms 才是交付口径。此前所有 61-min 数据、交付的 mic_asr_app.py 端到端验证，用的都是 640 ms 块； 本次为与 CUDA 报告严格对照，额外补测了一组 320 ms。 同一脚本、同一模型、同一段音频，只改一个 --chunk-ms： 两个 RTF 都是真的，差异全部来自块长，不是性能回归。

为什么块长减半，RTF 几乎翻倍？ 因为每块的成本里大头是"与块长无关的固定开销"：segment encoder 每个 chunk 都要 把整段累积音频重新编码一遍（无 window cache），decoder 也要对整个已生成前缀做一次 prefill。 块长从 640 → 320 ms，每块成本只从 360.7 ms 降到 322.6 ms （省 11%），但块数从 11 涨到 22（翻倍）—— 净结果是总处理时间 4.33 s → 7.42 s，涨 +72%（×1.72）。 换句话说：块长减半只省下 11% 的单块成本，却要付 2 倍的块数—— 短块买不到等比例的性能，只买到了更细的增量粒度。
所以本报告的读法：主指标（RTF / 稳态吞吐）看 640 ms 那一行 —— 那是交付配置； 320 ms 那一行只用于回答"和 CUDA 同块长时谁更快"这一个问题。

口径与局限（请 reviewer 重点看）

1. 速度对比是「iGPU vs dGPU」，不是「同硬件上的运行时对比」。 本机 GPU.1 恰好就是 RTX 5050 Laptop，我们本想让 OpenVINO 也跑在这块卡上， 从而把「运行时/量化差异」与「硬件差异」分开。但这条路走不通：OV 2026.4 的 intel_gpu 插件 能枚举到 GPU.1（能力报 FP32 / BIN / INT8，不含 FP16），而 encoder IR 的常量是 FP16； 编译到 convert:Convert_23531 这个 F16→F32 reorder 节点时 kernel_selector 找不到可用实现，compile_model 直接抛 RuntimeError。 f32 / f16 / 默认 / HETERO 四种配置全部失败。 所以表中 5.91× 的差距里同时包含「iGPU 算力弱于 dGPU」和「OV 运行时开销」两部分， 本报告无法进一步拆分。
2. CUDA 侧只引用、未重跑。audio.cpp 是独立二进制，不在本仓库构建链路内； CUDA 数字来自 confucius4-r2t2/stream_report.html 与 stream_metrics.csv （2026-10-08 测）。两侧采样间隔统一 250 ms、字段同名同单位； 但进程内存口径 RSS/USS vs Windows WorkingSet/Private 是近似对应——趋势可比，绝对值不可逐字节比。
3. 6.74 s 是极短样本，墙钟里的一次性开销占大头。 CUDA 的 3.67 s 墙钟中约 2.2 s 是模型加载 + CUDA Graph 预热； OV 侧我们把编译（约 6.9 s）与预热排除在计时之外。 因此直接比 RTF 对 CUDA 不公平。更干净的指标是稳态每块延迟： CUDA 55.5 ms vs OV iGPU 328.0 ms（同为 320 ms 块）。 交付口径（640 ms）下 OV 稳态每块 369.9 ms、预算占用 58%%， 换算成吞吐为 1.82× 实时。
4. 精度对比的参考不是人工转写。61-min 集的 reference 是 MiniMax 云端 asr-1.0， 故 7.88% / 7.69% 都是「相对云端 ASR」的误差，不等于相对人工转写的绝对 WER。
5. 混合集 MER 混了两种尺度。mix_60min 的 7.78% 里中文按字、英文按词， 是 CER 与 WER 的混合；英文侧 14.05% 与中文侧 6.77% 不能直接相减。

结论

精度 · OV 7.88% vs CUDA 7.69% 差距 0.19 pp，落在归一化口径波动（7.51–7.69%）范围内，可视为已追平。 关键结论：此前的 17.87% 并非 OV 精度问题，而是 max_new_tokens 被固定为 32、 错译了官方的自适应预算逻辑（C-047）。
速度 · iGPU 需要 640 ms 块才实时 交付口径（640 ms）下 OV iGPU RTF 0.642、稳态 1.82× 实时，61-min 全长实测 RTF 0.639、P95 0.675，满足 ≤0.8 验收线。 CUDA 在 320 ms 块下稳态 5.78× 实时，是 OV 的 3.18×。 若强行把 OV 也降到 320 ms 块，每块 322.6 ms、RTF 1.101，反而追不上实时流。 即：iGPU 方案成立的前提是接受 640 ms 的增量粒度。
实时性已被端到端验证 交付的 `mic_asr_app.py` 走的就是这套 640 ms 配置：麦克风 16 kHz 采集 → 在线 VAD （12–20 s 切段、切点对齐 chunk 边界）→ 增量解码 → GUI 实时上屏。60 s 连续实测 RTF 0.650、5 段定稿、文本连贯无跨段重复。也就是说上表的 RTF 不是 「离线跑批换算出来的理论值」，而是真实麦克风通路里跑出来的。
部署建议 - 有 NVIDIA 独显 → 继续用 CUDA / audio.cpp：每块 55–65 ms，余量充足，且不切段可到 240–300 s。
- 只有 Intel iGPU / CPU → OV 方案可用，但必须用 640 ms 块 + 12–20 s VAD 切段； 纯 CPU 推理 RTF 5–11，仅适合离线批处理。
- 两者都需要调用方自己做 VAD 切句：CUDA 超过 240–300 s、OV 旧 IR 超过 120 s 都会 OOM / 超上限。
