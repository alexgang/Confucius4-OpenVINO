4-bit 量化对比：CUDA Q4_K vs OpenVINO INT4

测量时间 2026-10-16 10:44 ｜ 同一台机器（RTX 5050 Laptop dGPU + Intel Xe3 iGPU）｜ CUDA 侧：audio.cpp v0.9.1，r2t2-q8_0.gguf vs r2t2-q4_k.gguf（由 HF 原始权重量化，同一段 6.74 s test.wav / 320 ms 默认策略 / 背靠背实测）｜ OV 侧：ov-int8-past vs ov-int4-lmhead-past（lm_head 全量 INT4，846 MiB——C-058③ 已换为头条构建；ov-int4-lmfp16-past 为次优构建，仅作对照）
本版已按 C-054 根因分析修订：OV INT4「变慢 15%」是单次测量噪声，5 次交替 A/B 取中位后 INT4 反而更快；性能与内存结论以 A/B 口径为准。

一句话结论

CUDA Q4_K：唯一划算的 4-bit 每块均值 64.3 → 61.0 ms（稳态 55.6 → 53.5 ms，快 3.7%）； 显存稳态 3120 → 2338 MB（-25.1%，权重缓冲 -35%）； WER 7.62% → 7.54%（-0.08 pp，噪声内无损）。适合需要同卡并发多路流式的场景。
OV INT4：不慢，但精度掉 1 pp 此前单次测量的「每块 360.7 → 415.4 ms（慢 15.2%）」经 C-054 复核为测量噪声： 5 次交替 A/B 取中位，INT4 每块 330.4 → 313.6 ms（快 5.1%）， prefill 88.1 → 81.6 ms（快 7.3%）、decode 192.6 → 182.6 ms（快 5.2%）； 内存也确实更省（工作集稳态 3246 → 2830 MB，-12.8%）。
精度：CUDA 无损，OV 掉 1.08 pp 61-min 集 WER：CUDA 7.62% → 7.54%（-0.08 pp，落在噪声内，可视为无损）； OV 7.88% → 8.96%（+1.08 pp，插入 363→427、替换 455→526，是真实退化， 与 C-044 teacher-forcing 的 top-1 84.3% vs 94.1% 一致）。
净结论 OV INT4 在 iGPU 上更快也更省，但不采纳 —— 原因是精度，不是性能；CUDA Q4_K 三个维度全赢，是唯一建议保留的 4-bit 选项。 C-043/C-044 早已证伪「量化是精度瓶颈」（真凶是 max_new_tokens 固定 32，C-047 修复），本次从性能侧给出同一方向的证据。

为什么 OV INT4 只小 ~10%：IR 构成拆解（C-055）

问题：CUDA 侧 Q4_K 比 Q8_0 小 35%，OV 侧 INT4 却只比 INT8 小 ~10%（模型文件 -9.1%、显存稳态 -11.1%）。 把 decoder IR 的每个 Const 按精度和语义拆开累加（c055_ir_breakdown.py， 合计与实际 .bin 字节数分毫不差），答案很清楚：INT4 的 IR 里 43% 的字节仍然是 FP16。

直接原因：lm_head 没被量化，且权重共享（tie）被打破

这个模型的输入 embedding 与输出投影本是同一份矩阵（weight tying，词表 151936 × 2048）：

用 OV API 追 lm_head MatMul 的权重输入可以实锤： INT8 指向 embed_tokens.weight/fq_weights_0（共享），INT4 指向独立的 self.model.thinker.lm_head.weight_compressed Const（element_type="f16" shape="151936,2048" size="622329856"）。 名字里的 "compressed" 名不副实——它在 IR 里就是未压缩的 FP16。光这一块就占了 INT4 文件的 41%。

两层稀释叠加在一起：
① 覆盖不全：词表矩阵占 FP16 基线的 18%（594/3282），INT4 对它几乎没压缩（还倒涨 25%）； 真正被压掉 74% 的 transformer 层占 82%，加权后整体只降 12.4%。
② 共用件未量化：两个 OV 配置还共用同一个 FP16 reviewer encoder（606 MiB，完全没量化）， 再稀释一层——「实际加载总量」从 2249 → 2045 MiB，只剩 -9.1%。
③ 量化格式开销：i4 按 group=128 打包（形状 [151936,16,128]），每组要带 f16 scale/zero-point， 对 128 个元素是 64B 数据 + 4B 参数 ≈ 6% 的额外开销——量级很小，不是主因。

如果 lm_head 也进 4-bit，能省多少？

C-056 真的导出了一个这样的变体（ov-int4-lmhead-past：不 clone、不 ignored_scope， embed 与 lm_head 共用同一份 i4 常量，tie 保留），实测 decoder IR = 846 MiB—— 比 995 MiB 的朴素估算还小（tie 保留意味着不必为 lm_head 再付一份 148 MiB）， 相对 INT8 是 -48.5%、相对现有 int4lmfp16 是 -41.2%， 已把 FP16 基线压掉 74%。换句话说，OV INT4「只小 10%」不是 4-bit 本身的极限， 而是导出配置的选择（lm_head 保 FP16 + tie 断裂 + encoder 未量化）。 精度和性能代价见下一节（C-056 实测：几乎为零）。

lm_head 为什么不量化？量化它会掉多少精度？（C-056 实测）

问题：既然 lm_head 的 FP16 让「INT4 省内存」基本落空，当初为什么把它留下？ 如果把它也量化成 INT4，精度会掉多少？—— 两个都实测了。

为什么没量化：一个被事后证伪的「保险」

构建说明（C-058③）：本报告的 INT4 头条已切换为 ov-int4-lmhead-past（decoder 846 MiB，lm_head 也进 INT4 且保持 tie）。ov-int4-lmfp16-past（1440 MiB，lm_head 保留 FP16）是次优构建，仅作对照。fresh-process 实测显示次优构建的显存差 / IR 体积差 = 1.72（异常），因其 594 MiB 的 FP16 lm_head 需额外运行时缓冲；全量构建该比值为 1.07（正常）。

① C-043 当时的诊断：10-13 10:45 的记录写着「lm_head (tied with embed_tokens) 量化误差是 第二个根因」，解决方案就是「保留 lm_head 为 FP16」（C-043#1 用于 INT8，C-043#3 备选 2 用于 INT4）。 交付的 ov-int4-lmfp16-past 由 c043_export_int4.py 产出： ignored_scope=[lm_head MatMul] + backup_mode=NONE（比 NNCF 默认还保守一档—— NNCF 在 INT4_SYM 下默认就会把最后一个 MatMul backup 成 INT8_ASYM）。
② tie 断裂是这个选择的机械副作用：脚本必须先 clone_tied_weight() 把共享常量复制一份， 才能做到「embed 进 i4、lm_head 留 FP16」——否则共用常量会被一起量化。
③ 事后看这个诊断是错的：C-043#1（INT8 + FP16 lm_head）被验证失败—— C-044 teacher-forcing 里 int8lmfp16 的 top-1 = 93.80%，反而比纯 int8 的 94.12% 还低； 真正的根因是 max_new_tokens 固定 32（C-047 修复）。C-044/C-053 也显示 INT4 的精度损失 主要来自 28 层 + embed，不在输出投影。也就是说：这份「保险」几乎没有赔过，却让 INT4 变体肥了 594 MiB。

结论：① 当初不量化 lm_head 是出于一个被证伪的诊断（「lm_head 量化误差是根因」）， 事后证明真正根因是 max_new_tokens；② 实测把 lm_head 也量化到 INT4， 精度没有可测量的损失（top-1 +0.64 pp、端到端 +2/213 token）， 体积再省 41.2%（decoder 1440 → 846 MiB，相对 INT8 -48.5%），还快 3.0%；
③ 但交付配置仍不变（INT8）——因为 INT4 相对 INT8 的 +1.08 pp WER 来自 28 层 + embed， 量化 lm_head 既不能挽回、也不会加重它。这条结论的价值在未来：若再导 4-bit 变体， 应全量量化 + 保持 tie（可再省 41%）；若想真正救回 INT4 的精度，方向在层间混合精度或 encoder 端， 而不是给 lm_head 上 FP16。

OV INT4 根因分析（C-054）

问题重述：C-053 单次测量显示 OV INT4 比 INT8 慢 15.2%（每块 360.7→415.4 ms）、prefill +51%（102.2→154.8 ms）。 这个结论不成立 —— 它是测量噪声。下面用四层证据给出真实图景。

证据 1 · 静态 IR 结构：INT4 把反量化写进了图

INT8 路径：u8 Const + 198 个 Subtract（zero-point 校正）→ MatMul； INT4 路径：197 个 i4 Const → Convert(i4→f16) → MatMul，反量化成为图里每拍都要执行的显式 op， 并额外多出 +197 Reshape / +55 Concat / +55 Broadcast / +200 Convert（合计约 500 个 op）；decoder IR 体积 1643→1440 MB（-12.4%）。 单看这张图，「INT4 图更大、op 更多，应该更慢」是合理推测 —— 但这只是推测。

证据 2 · 运行时 primitive：计算主体完全一致

编译后取 get_runtime_model() 的 ExecutionNode rt_info： 两边 FullyConnected 均 141 个、Gemm 均 1 个（计算主体一模一样）； INT4 多出一个 gather_ref__i4（i4 精度的 reference 实现，未走 XMX 快速路径）； INT8 有 113 个 dynamic_quantize_gpu_opt__f16（INT8 XMX 路径），INT4 为 112 个。 即 INT4 的额外成本集中在「反量化 / 重排」这类访存 op 上，不在计算量上。

证据 3 · 受控扫描：开销不随尺寸爆炸，权重收益占上风

对 standalone decoder IR 做双维扫描（中位耗时，ms）：Tt 1→256（Ta=50）：INT4/INT8 = 0.78–0.98×；Ta 50→1500（Tt=32，长前缀）：0.89–0.93×。 若「反量化开销」是主要矛盾，比值应随序列变长而恶化；实测全程 ≤1×、多数点 <1×，说明权重减半带来的访存收益占上风。

那「+51% prefill」是哪来的？—— 三类污染

① 单次测量的离群块：INT4 那一发出现了 904.6 ms 的离群块（INT8 最大 524.6 ms）。 即使在同一发测量内部，逐块中位也是 389.3 vs 389.5 ms —— 基本持平，是均值被离群值带偏。
② 61-min 长跑互相污染：INT4 的 61-min 跑测与 CUDA Q4 的 61-min 跑测并发执行，iGPU/dGPU 与主机互相抢资源， 该次 RTF 0.682 不能用于任何性能结论。
③ iGPU 共享本身的高方差：核显与桌面合成器、其他进程共享，单发测量的块间方差可达 ±30%， 任何「只跑一次」的跨配置对比在这台机器上都不足以下结论。

INT4 真实存在的两项成本

① 编译时间 6.75 → 10.94 s（+62%）：图里多出约 500 个 op，编译期常量反量化更贵。 对「起会话 → 说几句 → 结束」的短会话是实打实的启动代价；长流式会话可忽略。
② WER +1.08 pp（61-min，真实退化）：插入 363→427、替换 455→526， 与 C-044 teacher-forcing 的 top-1 84.3% vs 94.1% 互相印证。这才是 OV INT4 被否掉的真正原因。

结论与建议

交付配置保持不变 CUDA 侧继续 r2t2-q8_0.gguf（RTX 5050 上每块 55–65 ms，余量充足）； OV 侧继续 ov-int8-past + 640 ms 块。
如果目标是省内存 / 多路并发 CUDA 侧 Q4_K 是唯一划算的：显存稳态 -25.1%、权重缓冲 -35%、WER 仅 -0.08 pp（噪声内）、速度还快 3.7% —— 适合需要同卡并发多路流式的场景，切过去没有已知代价。
OV INT4：性能与内存双赢，但精度否掉 A/B 中位显示它在 iGPU 上更快（-5.1%）也更省（工作集 -12.8%、显存 -11.1%）， 但 WER +1.08 pp 是真实退化。唯一可考虑的场景：离线批处理 + 对精度不敏感 + 能接受 +62% 的编译启动开销。
不要再走「4-bit 换精度」的路线 与 C-047 的根因结论（max_new_tokens 固定 32）互相印证：这条模型的精度问题从来不在量化位宽。
两条可执行的后见之明（C-055/C-056） ① 若确需 4-bit：应全量量化 + 保持 tie——C-056 实测把 lm_head 也量化到 INT4 精度无可测损失 （top-1 +0.64 pp），decoder 再省 41.2%（1440 → 846 MiB），还快 3.0%； 当初给 lm_head 上 FP16 是「买错的保险」。② 若想再省内存：优先 encoder 端 （reviewer encoder 606 MiB 两边共用、未量化，量化它影响全部 226 段）而非继续动 decoder。
