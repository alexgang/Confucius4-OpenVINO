### 6.2 病根

`ext/bridge.py` 的**限长拆分**路径 `self._split_first_segment(segs)`

⇒ 下一轮 `if not self._first_seg_done:` **仍然成立**
⇒ 「**首段提前交付**」路径**又**跑一次
⇒ 而它**硬编码 `abs0 = 0`** ⇒ **把首段再交付一遍**。

### 6.3 修法（最小改动）

`ext/bridge.py`：dispatch 循环之后、`ready` 非空校验之后新增

```python
self._first_seg_done = True
```

⚠️ **不能**在 `ready` 为空时置位 —— 那会废掉「首段提前交付」这条优化
（首段还没到 3.5 s 时必须继续等）。

### 6.4 复现矩阵（修复后）

`first_speech` = 2.90 / 3.16 / 3.30 / 2.50 / 3.50 / 4.20 / 1.80

## 6bis. ★★ 本轮修的第二个真缺陷：「丢句」口径错误（静音填充段被误计为丢句）

### 6bis.1 缺陷陈述

`ext/bridge.py` 的 `adaptive_speed_stats()` 里：

```python
"n_dropped_dub": sum(1 for m in rows if not m.get("has_tts")),
```

⇒ **把「素材尾部静音填充段」（`has_tts=False` 且 `src_len=0`）也计成丢句**。

★ **实测证据**：run `20261105_172508` 的 `margin.json` 里
`adaptive_speed.n_dropped_dub` = **19**，而该 run 的 `per_segment` 中
`has_tts=False` 的段**全部**满足 `src_len == 0`（**19/19**）⇒ **真丢句 = 0**。

⇒ 与 EXT-009「**丢句必须为 0**（不改译文、不丢句、不回退到丢句）」**直接冲突**，
也会让 reviewer 误判为「丢了 19 句」。

### 6bis.2 修法（最小改动）

```python
"n_dropped_dub": sum(1 for m in rows
                      if not m.get("has_tts") and (m.get("src_len") or 0) > 0),
# ★ 单列：素材尾部静音填充段（**不是**丢句）
"n_silent_fill_segments": sum(1 for m in rows
                               if not m.get("has_tts") and (m.get("src_len") or 0) == 0),
```

⇒ `/status` 端点同步新增 `n_silent_fill_segments`（保持两端一致）。

3. 产物新增 `pct_caliber`（写明口径）＋ `p50_sec_interp_for_reference` /
   `p95_sec_interp_for_reference`（单列对照，不报数）。
