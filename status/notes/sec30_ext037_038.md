## 1. EXT-037 ②【BLOCKING】每段丢 3.5 s —— 已修

### 1.1 病根（reviewer EXT-037 ② 实测）

旧实现里，`ext/bridge.py` 在「首段已交付」分支里**每次**调用都执行：

```python
segs = split_first_segment_streaming(
    segs, cap_sec=self._first_seg_cut / float(C.SAMPLE_RATE),
    min_sec=C.SEG_MIN_SEC)
```

但前面把 `_buf` 裁掉之后，网格**已经是相对新缓冲的**
⇒ 函数仍把新缓冲开头的 `[0, 3.5 s)` 当作「已交付首段」去掉
⇒ **每段之后都丢掉 3.5 s**。

§29 旧轮次（run `20261104_195911`）的段区间实测：

```

↑ 每个缺口都正好 3.5 s
```

### 1.2 修法（最小改动，不偏离架构）

**守卫 = `_buf_base == 0`**（缓冲起点仍是会话起点 ⇒ 缓冲里**还留着**已交付的首段 ⇒ 需要对齐）：

```python
if self._buf_base == 0 and self._first_seg_cut:
    _segs = split_first_segment_streaming(
        segs, cap_sec=self._first_seg_cut / float(C.SAMPLE_RATE),
        min_sec=C.SEG_MIN_SEC)
    if not _segs:
        return None          # 网格还没成形 ⇒ 保留 _first_seg_cut ⇒ 下轮重试
    segs = _segs
```

**清零时机**：只在**真正裁掉缓冲之后**（`_buf_base` 推进）才 `self._first_seg_cut = 0`。

> ⚠️ 为什么不能提前清零：提前交付时**故意不裁 `_buf`** ⇒ 若此时清零，缓冲还没被裁
> ⇒ `_buf_base` 仍为 0 ⇒ 下一轮**不再对齐** ⇒ 原始网格的第一段被**重复派发**（与已交付首段重叠）。

**配套**：`flush()` / `PipelineSession.flush()` 必须**跳过「已交付但仍在缓冲里」的前缀**
（新增 `self._buf_delivered_prefix`），否则尾段会从 `_buf_base` 开始 ⇒ 与首段**重叠**。
