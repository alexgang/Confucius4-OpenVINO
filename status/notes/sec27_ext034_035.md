## 2. EXT-034① 同步/时长比只覆盖 7/13 段 —— 根因与修法

### 2.1 双重根因（reviewer 已核实为真，本轮定位到机制）

| # | 根因 | 机制 |

| ① | **onset 配对被抢** | `onDubOnset()` 用 `PAIR_WINDOW_SEC = 0.25` 找「最近的排程」配对 ⇒ **后一段的排程会抢走前一段的 onset**。实测 `metrics.dubOnsets` 里出现 **50 ms 间隔的连续 onset** ⇒ 同一段被记成多条、另一段一条都没有 |

**主口径换成「排程起点」**：
- `scheduleDub()` 里 `src.start(when)` 的 `when` 就是 **Web Audio 的采样精确播放起点** ⇒ 拿它当 `actual`。

## 3. EXT-034② RTF 口径错 —— 三口径分列

### 3.1 reviewer 的批评（成立）

旧结论写「TTS RTF = 1.231 > 1 ⇒ 结构上不可能实时」。但 **1.231 不是 TTS 自身的 RTF**：
`1.231 = TTS 耗时 73.84 s ÷ 源音频时长 59.98 s` —— 其中**混进了「中文译文比英文原声长」**（1.196 倍）⇒ 用它判「TTS 引擎慢」是**口径错** ⇒ 归因会错。

### 3.2 三个口径（`ext/bridge.py::compute_rtf_breakdown()`，落盘到 `margin.json` 的 `rtf_breakdown`）

| 口径 | 定义 | 含义 |
|---|---|---|
| `RTF_out` | `Σ tts_sec ÷ Σ speech_sec` | **TTS 自身**的 RTF（输出语音 vs 耗时）⇒ 这才是「TTS 引擎快不快」 |
| `speech_over_src` | `Σ speech_sec ÷ Σ 源音频秒` | **译文比原声长多少**（中文 vs 英文）⇒ 与 TTS 快慢**无关** |
| `tts_over_src` | `Σ tts_sec ÷ Σ 源音频秒` | **端到端占用率**（旧口径 1.231 就是它）⇒ 受上面两个**同时**影响 |

**旧数据复现验证**（用 `20261102_121431` 的真实 `margin.json`）：
`RTF_out = 1.029` / `speech_over_src = 1.1964` / `tts_over_src = 1.231` ⇒ 与 reviewer 的数字**逐位一致** ⇒ 口径正确。

**新轮实测**（`20261102_213515`）：
`RTF_out = 1.1937` / `speech_over_src = 1.2227` / `tts_over_src = 1.4595`
（totals：`tts_sec=87.5682` / `speech_sec=73.36` / `src_sec=60.0` / `asr_sec=48.7383` / `mt_sec=10.6018`）

⇒ **结论修正**：真正的瓶颈是 **TTS 自身 `RTF_out = 1.1937 > 1`**（译文变长只占 `speech_over_src`，已单列不混入）⇒ **TTS 提速是 EXT 改不动的**（引擎属其它模块）。

## 4. EXT-034③ / ④ 首段切太长 + ASR 时机 + 所需 D

### 4.1 ASR 调用时机（EXT-034④ 明确要求说明）

**ASR 是「整段音频完整到达后才调用」**（`ext/bridge.py::_dispatch_segment` 只在整段音频到齐后才调 `_process_segment`）⇒ ASR/MT/TTS **都**在那一刻才开始跑
⇒ **起步耗时 ≈ 首段长度 + ASR + MT + TTS**。

### 4.2 首段限长的实现（踩了三次坑才做对）

**最终方案**：在 **`ext/bridge.py` 的会话级**把首段**拆成两段**（`Session._split_first_segment()`），**分段器 `plan_segments()` 保持与 R2T2 逐位一致**。

**为什么不在分段器里限长**（踩坑记录）：
- 流式下缓冲区每处理一段就被裁掉（`self._buf = self._buf[cut:]`）⇒ **「缓冲区第一段」每轮都不同**
- ⇒ 若在分段器里按「缓冲区第一段」限长 ⇒ **每一轮的第一段**都被限短 ⇒ 等于把**所有段**都变成 3.5 s ⇒ 段数暴增、切点栅格整体平移
- ⇒ 实测 60 s 输入的尾部残留从 4 s 变 0.5 s ⇒ 低于 `flush` 的「尾部不足 1 s 丢弃」门槛 ⇒ **尾段被丢** ⇒ 既有断言变红。

**为什么「拆两段」而不是「截短」**：
- 截短 ⇒ 平移栅格 ⇒ 尾部残留变少 ⇒ 尾段被丢。
- 拆两段 ⇒ 首段 `[0, cap]` + 第二段 `[cap, 原切点]` ⇒ **后续所有切点逐位不变** ⇒ 尾段行为与原来**完全一致** ⇒ 唯一差别 = 首段更早起步。

**碎片保护**：第二片若 < `SEG_MIN_SEC`（3 s）⇒ **不拆**（不出碎片段）。
**取值**：`FIRST_SEGMENT_MAX_SEC = 3.5`（`ext/config.py`，含完整理由注释）。

```
D_required ≈ startup_sec + steady_sec + safety_sec
  startup = 首段长度 + 首段 ASR + MT + TTS     （实测 3.5 + 2.448 + 0.55 + 3.245 = 9.743）
```
